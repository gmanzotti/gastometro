2. ANÁLISE CRÍTICA DO PLANO
────────────────────────────────────────────────────────────────────

2.1 PONTO FORTE — A DISTINÇÃO DE AUDIÊNCIAS É REAL E DEFENSÁVEL
  O produto público (A) e o produto interno (C) servem públicos completamente
  diferentes:
    Produto A → qualquer pessoa, aberto, advocacy político, imprensa, redes
    Produto C → filiados, uso interno, dashboards corporativos
  Isso não é só argumento retórico: tecnicamente, Power BI não pode ser
  acessado sem login. Streamlit pode ser público. São funções incompatíveis.
  Essa distinção é o eixo central da estratégia argumentativa na reunião.

2.2 FALHA LÓGICA CRÍTICA — O CONTADOR NÃO EXISTE EM POWER BI
  O contador (dashboard/app.py linhas 780–865) é HTML+JavaScript puro:
  calcula R$/segundo com base em uma taxa pré-computada e atualiza o display
  a cada 100ms. É o elemento-âncora do produto público — visualmente, é o
  Gastômetro.

  Power BI não suporta JavaScript customizado desse tipo. O visual "HTML
  Content" do Power BI é removido do AppSource há anos por segurança.
  Plug-ins de terceiros (ex: HTML Viewer) são instáveis e não permitidos em
  ambientes corporativos com governança de TI. Conclusão: o contador não
  pode ser replicado em Power BI. Isso, por si só, inviabiliza o Power BI
  como substituto do produto público.

2.3 FALHA LÓGICA — "ANEXAR O DASHBOARD AO POWER BI DA CASA"
  Se o Power BI da casa é para filiados (acesso restrito), adicionar o
  Gastômetro ali não resolve o objetivo da presidência, que é comunicação
  EXTERNA e aberta. Os dois produtos não são intercambiáveis. Propor os dois
  em paralelo é correto, mas é preciso deixar claro que o Power BI não
  substitui o site público — complementa para um público diferente.

2.4 GARGALO TÉCNICO — POWER BI E AUTOMAÇÃO DE DADOS
  O pipeline atual gera arquivos .parquet e .json em data/. Power BI lê esses
  formatos, mas com restrições importantes:

    a) Arquivos locais: Power BI Desktop lê, mas Power BI Service (cloud,
       que é o que os filiados acessam online) NÃO lê arquivos locais
       diretamente. Precisa de um "gateway de dados" instalado em uma máquina
       sempre ligada na rede da FIESP, ou os dados precisam estar em:
       - SharePoint / OneDrive da FIESP
       - Azure Blob Storage
       - Azure SQL Database
       - Qualquer fonte cloud que o Power BI Service suporta nativamente

    b) Atualização automática: o Power BI Service pode agendar refreshes,
       mas depende da solução de gateway. Sem isso, os dados do Power BI
       ficam estáticos — atualização manual, o que derrota o propósito.

    c) Conclusão: para o Power BI funcionar de verdade como produto vivo
       (não congelado), a TI precisaria configurar um gateway ou hospedar
       os dados em algum serviço Azure. Isso é TRABALHO DA TI, não nosso.
       Na reunião, deixar claro que essa infraestrutura é responsabilidade
       do setor de TI, não da Assessoria Econômica.

2.5 GARGALO TÉCNICO — AZURE DEVOPS E STREAMLIT CLOUD
  Hoje o deploy do Streamlit está em gastometrofiespv1.streamlit.app, que
  deploya automaticamente a partir do GitHub. Se migrarmos o repositório para
  Azure DevOps, essa integração automática quebra — Streamlit Community Cloud
  não conecta com Azure DevOps.

  Soluções possíveis:
    Opção 1: Manter GitHub + espelhar para Azure DevOps (mirror)
      - Git suporta múltiplos remotos. Um push vai para os dois.
      - Streamlit Cloud continua funcionando via GitHub.
      - TI tem visibilidade e acesso no Azure DevOps.
      - Custo de implementação: 1 linha de configuração no git.

    Opção 2: Migrar completamente para Azure DevOps + trocar host do site
      - Sair do Streamlit Cloud para um servidor próprio (ex: Azure App
        Service, container Docker, VM da FIESP).
        A TI provavelmente gostaria disso — voltam a ter controle de hosting.
      - Custo: infra adicional, possível custo de servidor, configuração de
        CI/CD no Azure DevOps para fazer deploy automático.
      - Vantagem: tudo dentro do ecossistema Microsoft que a TI já usa.

    Opção 3: Manter GitHub, recusar DevOps
      - Politicamente mais arriscado dado o contexto.
      - Desnecessário se a Opção 1 resolve.

  RECOMENDAÇÃO: propor a Opção 1 imediatamente (mirror) e a Opção 2
  como evolução futura quando o produto estiver estabilizado.

2.6 GARGALO TÉCNICO — GERAÇÃO DO PDF PARA WHATSAPP
  O plano é enviar um PDF com a Tab 0 (Gastos do Gov Federal), substituindo
  a seção "Explorador de Despesas" pelo gráfico "Trajetória Fiscal —
  Resultado Primário acumulado 12 meses" da Tab 1.

  O PDF precisa ser gerado programaticamente (não manualmente) para
  funcionar junto com a automação de atualização de dados. Opções técnicas:

    a) weasyprint / reportlab: gera PDF a partir de HTML/Python.
       Pró: leve, sem dependências de browser.
       Contra: os gráficos Plotly são JavaScript — não renderizam em PDF
       via weasyprint. Precisariam ser exportados como imagens primeiro
       (fig.to_image() via kaleido).

    b) playwright / selenium: abre o browser, navega até o dashboard,
       tira screenshot e converte para PDF.
       Pró: captura o visual exato do dashboard.
       Contra: pesado, precisa de browser headless instalado no servidor.
       O contador JavaScript ficará com o valor do momento do screenshot.

    c) Template HTML estático + kaleido para os gráficos (recomendado):
       Criar um script que:
       1. Gera os gráficos Plotly como imagens PNG (fig.to_image())
       2. Monta um HTML com os grandes números + imagens
       3. Converte o HTML para PDF com weasyprint
       Pró: controlado, sem browser, leve, visual próximo ao dashboard.
       Contra: não é idêntico ao dashboard — é uma versão editorial do PDF.

  RECOMENDAÇÃO: Opção (c). O PDF não precisa ser uma cópia pixel-perfeita
  do dashboard — pode ser um relatório editorial mais limpo, inclusive mais
  adequado para envio por WhatsApp (leitores de PDF mobile preferem layouts
  simples).

2.7 GARGALO TÉCNICO — WHATSAPP BUSINESS API
  Mensagens proativas (o usuário não iniciou o chat) via WhatsApp exigem:

    a) Conta WhatsApp Business API (não o app comum): precisa de aprovação
       da Meta e um provedor de acesso, ex: Twilio, 360dialog, Zenvia,
       ou diretamente a Meta Cloud API.

    b) Templates de mensagem pré-aprovados pela Meta: o template enviado
       precisa ser submetido e aprovado antes do uso. O processo leva de
       1 a 7 dias. O template com variáveis dinâmicas (mês, despesas, RP)
       precisa ser formatado no padrão exato da Meta.

    c) Custo por mensagem: cada mensagem template enviada tem custo
       (varia por provedor, ~R$ 0,15–0,40/mensagem). Se a lista de contatos
       for pequena (presidência, equipe, imprensa selecionada), o custo é
       negligenciável. Se for ampla, precisa de orçamento.

    d) Lista de contatos: os destinatários precisam ter optado por receber
       mensagens (opt-in). Isso é uma exigência da Meta, não só burocracia.
       Enviar para contatos sem opt-in pode resultar em bloqueio da conta.

  RECOMENDAÇÃO: Iniciar o processo de aprovação da conta e do template COM
  URGÊNCIA — é o item com maior lead time do projeto. A automação técnica
  de envio é simples depois que a conta estiver aprovada.

2.8 RISCO DE DUPLA MANUTENÇÃO
  Manter site público (Streamlit) E dashboard interno (Power BI) cria dois
  produtos que precisam evoluir juntos. Toda mudança de metodologia, nova
  série de dados, ou ajuste visual precisa ser implementada duas vezes.

  Isso é gerenciável agora porque o Power BI é uma concessão à TI, não o
  produto principal. Mas precisa ficar claro internamente que o Streamlit
  é o produto master e o Power BI é um derivado. Se a TI tentar inverter
  essa hierarquia, o risco de fragmentação aumenta.

4. ESTRATÉGIA ARGUMENTATIVA PARA A REUNIÃO
────────────────────────────────────────────────────────────────────

4.1 PRINCÍPIO GERAL
  Não tratar as ferramentas da TI como ameaça nem como imposição. Tratar
  como complemento válido, desde que o produto público sobreviva intacto.
  A presidência tem a palavra final — mas a negociação amigável é preferível.

4.2 SOBRE O STREAMLIT vs. POWER BI
  Argumento técnico (não político):
    "Power BI não suporta contador em tempo real com JavaScript customizado.
    O contador é o elemento central do produto que a presidência pediu — é o
    que faz o Gastômetro ser diferente de um dashboard corporativo padrão.
    Não é uma preferência de ferramenta: é uma limitação técnica objetiva."

  Argumento de audiência:
    "O site público serve quem não é filiado — imprensa, público geral,
    governo. Power BI exige login da FIESP. São públicos diferentes, não
    concorrentes. Podemos ter os dois: o site público fica em Streamlit,
    e os filiados acessam uma versão interna em Power BI."

  Concessão estratégica:
    "Topo construir o Power BI para os filiados. Mas a infra de gateway e
    publicação no Service é com a TI — eu entrego os dados no SharePoint."

4.3 SOBRE O AZURE DEVOPS
  Aceitar imediatamente, com a ressalva do mirror:
    "Perfeito. Podemos configurar o mirror hoje — o código vai para o Azure
    DevOps automaticamente a cada push. O GitHub fica só como ponto de
    deploy do Streamlit Cloud. Quando mudarmos o hosting, desligamos o
    GitHub."

4.4 SOBRE O WHATSAPP
  Apresentar como demanda da presidência (não nossa):
    "O envio de mensagens via WhatsApp quando a base atualiza foi pedido
    explicitamente. Já sabemos que é pago — precisamos definir quem aprova
    o orçamento e quem registra a conta Business na Meta."

  Isso coloca a TI no papel de parceiro para resolver, não de obstáculo.

4.5 SEQUENCIAMENTO SUGERIDO PARA NEGOCIAR
  Prioridade 1 (fazer agora, não depende da TI):
    - Mirror GitHub → Azure DevOps
    - Iniciar aprovação WhatsApp Business API

  Prioridade 2 (fazer logo, produto público):
    - Hospedar site em domínio FIESP (pode ser Streamlit Cloud com domínio
      customizado, ou Azure App Service se a TI preferir)

  Prioridade 3 (fazer depois, concessão à TI):
    - Power BI interno, com dados no SharePoint
    - TI configura gateway de dados
